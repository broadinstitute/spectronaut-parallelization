# Parallel Spectronaut Workflow

This repository provides an updated Spectronaut pipeline that parallelizes DIA/SWATH searches on Google Cloud using WDL. The new `spectronaut-parallel/parallel_spectronaut.wdl` workflow expands upon the original `spectronaut-with-conversion/Spectronaut_v20-0.wdl` by adding automated manifest generation, conversion fan-out, shard-level search, and SNE consolidation to better support large HTRMS datasets.

## Features 
- **Full pipeline orchestration.** Adds explicit staging steps (`list_files`, `gather_htrms`, `partition_htrms_manifest`, `collect_sne_manifest`, `combine_sne`) so conversion, search, and reporting run end to end from a GCS directory.
- **Parallel search sharding.** Splits the HTRMS manifest across multiple VMs (`search_vm_count`) and ensures shard outputs use deterministic experiment names (`experiment_name_vmNNN.sne`), then recombines them.
- **Flexible manifest sourcing.** Automatically builds manifests from a `gs://` folder or accepts a user-supplied manifest when present; prioritizes supplied manifests to avoid duplicate discovery work.
- **Conversion fan-out.** Converts source files to HTRMS in parallel when `do_conversion` is enabled, reducing wall-clock time for large cohorts.
- **Artifact tracking.** Emits manifests of discovered inputs, conversion outputs, shard-level SNEs, combined archives, and per-shard output directories for downstream inspection.
- **Resource tuning.** Exposes CPU, memory, and disk settings for both search shards and the combine step so runs can be right-sized for the input scale.
- **Improved error handling.** Validates Spectronaut exits, verifies SNE presence, and records the final `.sne` filenames to align Cromwell outputs with Spectronaut experiment names.

## Workflow Overview
1. **`list_files`** – enumerates objects in the provided `gs://` folder.  
2. **Conversion (optional)**  
   - `htrms_conversion` scatters across input files to convert to HTRMS.  
   - `gather_htrms` collects produced HTRMS locations into a manifest.  
3. **Manifest resolution** – selects the best manifest to drive search (`htrms_manifest_input` > conversion manifest > directory manifest).  
4. **Search (optional)**  
   - `partition_htrms_manifest` divides inputs into batches.  
   - `spectronaut_search_vm` runs Spectronaut per batch; each shard writes its `.sne` and full output directory.  
5. **`collect_sne_manifest`** – converts shard outputs to a combined manifest (GCS paths preferred).  
6. **`combine_sne`** – merges shard SNEs, generates optional reports, and packages the combined output.

## Choosing Conversion and Search Modes
- **Convert and search (`do_conversion=true`, `do_search=true`)**  
  Use when you start from raw vendor formats and want the pipeline to produce HTRMS and immediately search. Provide `file_directory` pointing at raw files; the workflow scatters conversion, then continues into search with the converted manifest.

- **Search pre-converted data (`do_conversion=false`, `do_search=true`)**  
  Provide a directory containing existing HTRMS files, or supply `htrms_manifest_input`. The workflow will either build a fresh manifest from the directory or rely on the provided manifest.

- **Conversion only (`do_conversion=true`, `do_search=false`)**  
  Enables parallel conversion and emits the conversion manifest without performing any search or combine steps.

- **Search only (`do_conversion=false`, `do_search=true`, `htrms_manifest_input=...`)**  
  Skips manifest creation work by using your curated manifest. Ideal when you keep a controlled list of HTRMS objects or want to retry searches with the same inputs.

- **Skip Spectronaut entirely (`do_search=false`)**  
  Useful for verifying discovery/manifests or debugging conversion issues before running the heavier search stage.

`skip_conversion` is automatically engaged when `htrms_manifest_input` is provided alongside `do_search=true`, ensuring the workflow does not redundantly convert files you already staged.

## Key Inputs
- `file_directory` – GCS directory containing raw files or HTRMS files. Must start with `gs://`.
- `experiment_name` – base name applied to each shard (`_vmXXX`) and to the combined SNE.
- `convert_schema` – optional Spectronaut conversion schema passed to each conversion shard.
- `htrms_manifest_input` – optional manifest file listing HTRMS objects (one per line, typically GCS URIs).
- `search_vm_count` – maximum number of parallel search shards; actual shard count equals batches created.
- `search_cpu`, `search_memory_gb`, `search_disk_gb` – per-shard resource settings.
- `sneCombine_disk_gb` – disk allocation for the combine step.
- Spectral search assets: `fasta_1` (required), plus optional `fasta_2/3`, `spectral_library_1/2`, `analysis_settings`, `enzyme_database`, `json_settings`, and report schemas.

## Outputs
- `discovered_inputs` – manifest generated by `list_files`.
- `converted_htrms` – per-shard conversion outputs (if conversion ran).
- `htrms_manifest` – manifest actually used for search partitioning.
- `vm_sne_files` – list of shard-level `.sne` files.
- `vm_search_outputs` – directories holding each shard’s Spectronaut run (logs, reports, etc.).
- `sne_manifest` – manifest of shard SNE locations, transformed to GCS paths where possible.
- `combined_sne_output` / `combined_sne_files` / `combined_sne_archive` – combined results and zip archive from `combine_sne`.

## Usage Tips
- Keep `experiment_name` unique per workflow run to avoid collisions in long-lived GCS folders.
- Inspect `collect_sne_manifest.sne_manifest` to confirm generated GCS URIs before launching downstream analytics.
- Tune `search_vm_count` based on dataset size and available quota; too many shards can increase per-VM overhead.
- If Spectronaut requires custom enzyme databases, set `enzyme_database` to ensure each shard imports it prior to search.
- Logs from each shard are copied into `spectronaut_vm_output/spectronaut_vm.log`; examine them when diagnosing missing `.sne` files or Spectronaut errors.

## Troubleshooting
- **Missing `.sne` output** – check the shard log to confirm Spectronaut completed successfully. The workflow expects a file named after the shard (`experiment_vmNNN.sne`); any divergence will be renamed and logged.
- **Empty manifest errors** – ensure `file_directory` is correct and accessible, or provide an explicit manifest.
- **Disk exhaustion** – increase `search_disk_gb` or `sneCombine_disk_gb`, especially for large libraries or many HTRMS inputs per shard.
- **Combine failures** – confirm all shard SNEs localized; `combine_sne` validates file presence before invoking Spectronaut.

For development or smoke tests, run a small manifest (one to two files) with `search_vm_count=1` to verify configuration before scaling out.
